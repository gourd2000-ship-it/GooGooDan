# 구현 계획: 학생 계정·학습 현황 관리

## 개요

확정된 학교별 전용 주소와 Google Workspace 관리자 로그인을 기반으로, 학생 영속 계정과 성취 관리 기능을 만든다. 이 계획은 **구조 → 공통 기능 → 개별 기능** 순서이며, 세부 작업은 [todo.md](./todo.md)에 있다.

## 확정 아키텍처

- 호스트명은 `school_id`로 해석한다. 모든 학생·기록·관리자 쿼리는 이 학교 범위를 강제한다.
- 관리자는 Google OpenID Connect ID 토큰을 서버에서 검증하고, 허용된 Workspace 정책과 학교 역할을 확인한다.
- 학생은 학년·반·4자리 PIN으로 로그인하지만, 실제 소유권은 불변 `student_id`로 판정한다.
- 학생·관리자 세션은 분리된 서버측 해시 토큰과 `HttpOnly` 쿠키를 사용한다.
- 원본 기록은 보존하고 랭킹·대시보드에서만 학생별 최고 기록을 집계한다.

## 의존성 그래프

```text
학교 호스트/Google 관리자 인증/DB 스키마
                 ↓
학생 세션 + 학교 권한 + 기록 소유권 + 최고점 집계
                 ↓
학생 로그인·프로필·랭킹 | 관리자 명부 | 관리자 대시보드
```

## 단계별 검증

### 구조 체크포인트

- [ ] 호스트가 학교를 정확히 식별하고 타 학교 데이터는 거부된다.
- [ ] 유효 Google Workspace 관리자만 관리자 API에 접근한다.
- [ ] 마이그레이션은 기존 익명 기록을 보존한다.

### 공통 기능 체크포인트

- [ ] 새로고침 가능한 학생 세션, 기록 귀속, 최고 기록 집계 API 테스트가 통과한다.
- [ ] 말하기와 누르기가 같은 학생 ID로 기록된다.
- [ ] 클라이언트 빌드가 성공한다.

### 개별 기능 체크포인트

- [ ] 학생 로그인/프로필/랭킹과 관리자 명부/대시보드 UI 테스트가 통과한다.
- [ ] 실제 HTTPS 배포에서 Google 로그인과 세션 쿠키가 동작한다.

## 병렬화

- 구조 단계의 DB 마이그레이션과 Google 설정 문서는 병렬 준비할 수 있지만 적용은 순차적이다.
- 공통 API 계약이 확정된 뒤 학생 UI와 관리자 UI는 병렬로 만들 수 있다.
- 기록 집계 API와 대시보드 UI는 응답 타입 확정 후 병렬로 진행한다.

## 위험

| 위험 | 완화 |
| --- | --- |
| Google 로그인 설정 오류 | 개발·운영 리디렉션 URI와 허용 도메인을 별도로 점검 |
