# 말하는·누르는 구구단 로드맵

개발은 **공통 기능을 완성·검증한 뒤 개별 게임 모드를 순차적으로** 추가한다. 모든 마일스톤은 테스트를 먼저 실패시키는 RED 단계에서 시작해 최소 구현으로 GREEN을 만든다.

## M0. 계획 승인 (현재)

- [x] 말하기·누르기 분리 요구사항 작성
- [x] 누르는 구구단의 답·식·혼합 게임 모드 작성
- [x] 공통 기능 → 개별 기능 순서와 TDD 계획 작성
- [ ] 사용자 승인 후 개발 시작

승인 전에는 코드, 패키지 의존성, DB 스키마를 바꾸지 않는다.

## M1. 공통 도메인 규칙과 테스트 기반

**목표:** 모든 누르는 게임 모드와 말하기가 공유하는 문제·점수·검증 기반을 만든다.

- 클라이언트 단위 테스트 실행 환경(Vitest, React Testing Library)을 추가한다.
- 10개의 중복 없는 문항 순서(순서·역순·섞기)를 생성한다.
- 숫자 보기와 식 보기 각각에서 정답 하나·고유한 오답 세 개를 생성하는 공통 계약을 만든다.
- 답안 판정, 난이도별 점수, `answer | expression | mixed` 게임 모드 타입을 순수 로직으로 분리한다.

**TDD 완료 기준:** 문항 순열, 보기 유일성, 정답 포함, 점수 계산의 RED 테스트가 먼저 확인되고 GREEN이 된다.

## M2. 공통 누르는 구구단 흐름과 홈 설정

**목표:** 모든 누르는 게임 모드가 재사용할 화면 흐름과 설정을 만든다.

- 홈에서 말하기/누르기 카드 중 하나만 활성화하는 상태를 구현한다.
- 누르는 카드 안에 답 고르기·식 고르기·답과 식 섞기 선택을 추가한다.
- 공통 4지선다 화면 틀, 선택 잠금, 접근 가능한 정오답 피드백, 800ms 자동 전환, 결과 전달을 구현한다.
- 말하기 흐름은 기존 녹음·AI 채점을 그대로 사용하며, 공통 문항 순서만 사용한다.

**TDD 완료 기준:** 비활성 카드 입력 차단, 선택 설정 전달, 한 번만 답안 선택, 마지막 문제 결과 전환을 컴포넌트 테스트로 검증한다.

## M3. 개별 기능 1 — 답 고르기

**목표:** 식을 보고 숫자 답을 고르는 모드를 완성한다.

- `3 × 4 = ?` 형식의 문제와 숫자 보기 4개를 공통 흐름에 연결한다.
- 숫자 오답 3개가 중복·정답 중복 없이 생성되는지 검증한다.
- 답 고르기 10문제 완료와 결과 표시를 확인한다.

**TDD 완료 기준:** 숫자 보기 구성, 정답/오답 피드백, 10문제 고유성의 실패 테스트를 작성한 뒤 통과시킨다.

## M4. 개별 기능 2 — 식 고르기

**목표:** 숫자 답을 보고 올바른 곱셈식을 고르는 모드를 완성한다.

- `12 = ?` 형식의 문제와 식 보기 4개를 공통 흐름에 연결한다.
- 오답 식이 표시 숫자를 만들지 않고, 네 식이 서로 다른지 검증한다.
- 식 고르기 10문제 완료와 결과 표시를 확인한다.

**TDD 완료 기준:** 식 보기의 정답성·고유성, 피드백, 중복 없는 출제의 실패 테스트를 작성한 뒤 통과시킨다.

## M5. 개별 기능 3 — 답과 식 섞기

**목표:** 한 연습 안에 답 고르기와 식 고르기를 모두 제공한다.

- 10문제를 답 고르기 5개와 식 고르기 5개로 배정하고 순서 규칙에 맞게 섞는다.
- 각 문제에 맞는 숫자 또는 식 보기를 표시한다.
- 출제 문제의 곱셈식이 중복되지 않음을 보장한다.

**TDD 완료 기준:** 두 형식이 각 5개씩 포함되는지, 각 형식의 보기 계약과 10문제 고유성이 유지되는지 테스트한다.

## M6. 기록 API와 방식별 명예의 전당

**목표:** 누르는 게임 모드 정보를 포함해 기록을 안전하게 저장하고, 학습 방식별 랭킹을 보여 준다.

- `records.practice_type` 및 `records.tap_game_mode` 마이그레이션과 기존 말하기 기록 이관 절차를 추가한다.
- 서버가 누르는 기록의 게임 모드·정답 수·시간을 검증하고 점수를 계산해 저장하게 한다.
- 기존 말하기 저장에는 `speech`와 `NULL` 게임 모드를 명시한다.
- 명예의 전당은 말하기/누르기 최상위 탭으로 분리하고, 각 탭 안에서 단 필터를 제공한다.

**TDD 완료 기준:** 서버 단위 테스트로 게임 모드 검증·점수·저장 타입을, 화면 테스트로 방식별 랭킹 분리를 검증한다.

## M7. 회귀 점검과 배포 준비

**목표:** 두 학습 방식과 세 누르는 게임 모드를 배포 가능한 상태로 검증한다.

- 서버 테스트, 클라이언트 테스트, 린트, 프로덕션 빌드를 통과시킨다.
- 말하기, 답 고르기, 식 고르기, 혼합 모드 각각의 10문제 완주·기록·랭킹을 수동 점검한다.
- 데이터베이스 마이그레이션을 검토·적용하고, 코드 품질 검토 후 승인 범위에서 커밋·푸시·배포한다.

## 의존성 및 위험 관리

| 항목 | 대응 |
| --- | --- |
| 세 모드가 문제·보기 규칙을 중복 구현할 위험 | M1에서 순수 도메인 함수와 타입을 고정하고, M3~M5는 그 계약만 사용한다. |
| 섞기 모드에 한 형식만 우연히 나올 위험 | 무작위 독립 선택 대신 답 5개·식 5개를 명시적으로 배정하는 테스트를 둔다. |
| 식 오답이 우연히 같은 답이 되는 위험 | 식 고르기 생성기는 결과값과 식 문자열의 고유성을 모두 테스트한다. |
| 현재 클라이언트에 단위 테스트 도구가 없음 | M1에서 개발 의존성을 추가하고 첫 RED 테스트로 실행 경로를 확인한다. |
| 기존 랭킹 데이터에 방식·게임 모드 값이 없음 | 기본값과 제약 조건을 갖는 가역적 마이그레이션으로 기존 행을 `speech`/`NULL`로 이관한다. |
